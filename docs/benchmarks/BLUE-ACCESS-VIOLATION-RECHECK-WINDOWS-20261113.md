# Blue Engine benchmark access-violation recheck: Windows

The prior [bounded benchmark](BLUE-HINTS-WINDOWS-BOUNDED-20261113.md) recorded baseline executable SHA-256 `582cda7462ec785dde99c286718d2a72a92f9b9afa6635ddc2ba8b5426e19c1a` emitting a complete benchmark record and then exiting `0xC0000005` once; its other baseline run exited 0. Stderr was empty. The exact fault location and timing relative to shutdown were not captured.

On the same Windows host, without changing either binary, seven additional native `--benchmark` processes were run sequentially. In the order baseline, candidate, candidate, baseline, baseline, baseline, baseline, every process emitted a benchmark record and exited 0; every stderr file was empty. The candidate SHA-256 was `92bb5f4d13f3472a7a184dea26acd7a6a2e2821aaa470779df05c73f2779aded`. Together with the previous observations, the baseline produced one access-violation exit in seven observed runs; the candidate exited 0 in four observed runs. These are bounded observations under uncontrolled host conditions, not rates or proof that the candidate fixes the problem.

This exit-code-and-record loop did not reproduce the fault in the new runs, so it is not a reliable red-capable diagnostic loop. No cause was established, no specific cause was ruled out, and no production fix was made. `cdb`, `windbg` and `procdump` were not found on the current command search path; that does not establish whether debugging tools exist elsewhere. A reproducible failure or an appropriately captured crash dump with symbols would be needed to locate the fault. Raw stdout/stderr and outcomes remain in sibling workspace directory `blue-access-violation-probe-windows-20261113`; the original logs and binaries remain in `blue-hints-benchmark-windows-20261113`.
