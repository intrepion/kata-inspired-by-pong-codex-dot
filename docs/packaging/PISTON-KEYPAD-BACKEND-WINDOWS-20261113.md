# Piston keypad Enter: Windows backend source review

At checkpoint `37e45ce399b1b43768e37ea19586d768dbb399ce`, Piston adapter Git blob `55fb3e016612b2e9652702953e01450f254a201f` and lockfile blob `19f115c2915eb8124726aeb8726b5955ee3b4065` were inspected. Locked offline Windows MSVC `cargo tree -i` queries show `pong-piston -> piston_window 0.148.0 -> pistoncore-winit_window 0.20.5 -> winit 0.30.13`. The earlier [Windows release tests](PISTON-KEYPAD-ENTER-WINDOWS-20261113.md) inject Piston key values directly; they do not prove native mapping.

In the cached winit Windows source, physical `KeyCode::Enter` and `KeyCode::NumpadEnter` map to `VK_RETURN`; the logical non-character mapping maps that virtual key to `NamedKey::Enter`. Winit separately derives a Numpad location for extended Return and has a separate NumpadEnter physical code. The cached Piston window backend maps `input.logical_key` `Named(Enter)` to `Key::Return`, carries `PhysicalKey::Code` as an integer in `ButtonArgs.scancode`, and filters repeated presses using the last mapped logical key. The Pong adapter consumes `press_args` and `release_args` as keyboard keys without reading that physical-code field.

This supports the inference that ordinary Windows Enter and keypad Enter can reach the adapter as the same `Return` value through this locked backend, and that closely overlapping presses can be conflated by its logical-key repeat tracking. It does not establish an actual physical-input failure or guarantee mapping under every device, layout or event path. Merely reading the physical-code field in the app cannot recover a press that the backend has already discarded. No backend or dependency change was made.
