# Wry/Tao Pong security-boundary investigation

This is a feasibility investigation, not a replacement desktop application. The current Yew and Leptos Tauri configurations use an empty capabilities list and CSP `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; connect-src 'self'; object-src 'none'`. Their shared native demo has one opt-in scripted export command: it rejects more than 8 MiB, validates exact filenames and all scenario reports, creates files with create-new semantics only in a newly requested directory, and disables the command after completion. Normal play does not enable it. Existing wrappers and security configuration were not changed.

Inspection of locally cached Wry 0.57.2 found several requirements that a replacement must explicitly handle. Its documented custom-protocol origin differs across platforms, and `with_html` produces a null origin; neither supplies the current policy automatically. The Windows implementation installs the navigation callback on WebView2 `NavigationStarting`, and the code inspected does not establish subframe or subresource blocking. The documented Windows initialization script is injected into subframes even when main-frame-only is requested. The Wry IPC handler receives a request URL; Linux documentation says iframe requests can report the main-frame URL, so URL equality alone cannot establish frame identity across platforms. Wry's default download-start handler allows downloads. These are version-specific source/API observations, not a test of actual WebView behavior or a claim about all platform implementations.

A task-local no-IPC API fixture used Wry 0.57.2 and `url` 2.5.8. Its [source](../evidence/wry-security-api-probe-windows.rs), SHA-256 `d2826898a4f7d769e5415354af4fb1ba59b4b597a05b6771dba72c4f1adddc30`, constructs a builder with a fixed illustrative loopback document URL, a parsed exact main-document predicate, deny callbacks for new windows, downloads and permission requests, and disabled devtools. It registers no IPC handler or initialization script. Windows MSVC Rust 1.99.1 offline locked tests passed two cases: builder construction without creating a WebView, and a URL-predicate table covering the expected document and eleven rejected cases including different port, host, userinfo, path, query, fragment and scheme. The fixture lock SHA-256 is `da29d357be827ea4ad4339a1588ee566685605e932aa93c644aea73050bb3ab3`; Windows-filtered metadata had 69 resolved nodes with no license expression containing LGPL, GPL-3 or MPL. The fixture, lock, raw metadata and target remain in task workspace `wry-security-api-probe-windows-20261113`.

The fixture is deliberately incomplete and must not be run as a Pong wrapper: its port is a placeholder, it creates no listener, authenticates no server, supplies no CSP response, opens no WebView and exercises no browser or IPC events. Passing its model tests does not prove Wry calls the callbacks as intended, prevent local-server impersonation, secure subframes, establish WebView2 or cross-platform behavior, or qualify its dependencies. No actual Pong prototype or desktop package was implemented because these boundaries could not yet be validated with the available native window controls.

A safe next prototype needs, at minimum: an owned localhost-only listener established before launch with a per-session unguessable capability and exact host/path/method handling; fixed allowlisted assets and correct WASM MIME types; a verified response CSP at least as restrictive as the current policy; explicit navigation, new-window, permission and download handling; and no native command channel until frame/origin identity and message authorization can be demonstrated on each platform. If scripted export is added, preserve its one-shot enablement, size limit, exact filename and state validation, create-new writes and output-directory restrictions. Test adversarial origins, redirects, lookalike URLs, subframes, malformed/oversized messages, repeated calls and normal keyboard/focus behavior in actual supported WebViews served through localhost. Security equivalence, physical input, system licenses, clean-machine operation and release readiness remain open.
