# Kotlin diagonal collision correction

At checkpoint `ebe6265f49183a8598022eb9c837dbd905e2d227`, the new Windows JVM regression cases reproduced the diagonal collision mismatch and other contact-timing errors: four of the first four added cases failed before the fix. Kotlin now evaluates ball height and moving paddle position at the paddle-face crossing, accounts for a prior wall reflection, and advances the ball through the remaining time after contact, including a subsequent wall reflection. This follows the shared Rust core's bounded-step collision approach.

Windows MSVC-hosted Android Gradle 9.6.1, Microsoft JDK 21 and the existing Android SDK ran the complete isolated offline JVM unit suite after the fix: 15 GameTest, 2 ScenarioTest and 7 TouchInputTest tests passed, zero failures. The GameTest suite covers crossing-time hit/miss on both sides, prior wall bounce, player and CPU motion, paddle clamping, remaining travel and a wall bounce after either hit. The TouchInputTest suite includes the match-end regression introduced at `2468cea`. A separate isolated JVM probe compared all 13 `smoke-v1` checkpoints against `docs/evidence/rust-core-contact-timing-model-20261112.jsonl`: state, scores, paddle and ball values matched at the printed precision. The regular ScenarioTest also passed. This is model/replay evidence, not Android rendering, physical touch or device qualification.

The initial failing test report was observed before the fix; later successful Gradle runs overwrote its generated XML. The isolated project, successful probe XML and copied offline Gradle cache remain in the workspace under `android-nonplaying-windows-20261113` and `android-nonplaying-gradle-cache-20261113`. Swift remains a separate implementation and is not changed by this Kotlin fix. Mobile build, device, accessibility and release qualification remain open.
