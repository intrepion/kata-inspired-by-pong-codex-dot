# Notice preparation graph integrity

The notice builder previously iterated only package metadata whose IDs appeared in `resolve.nodes`; a resolved node with no corresponding package was silently omitted. A synthetic regression demonstrated that the builder could return an empty missing-notice list for the incomplete input. This could misrepresent the supplied graph's coverage.

Before building an index, the tool now requires nonempty unique resolved-node IDs, unique package IDs, a package record for each node, a represented root when supplied, and consistent dependency lists whose referenced nodes exist. Malformed or inconsistent inputs fail instead of yielding a misleading index. This checks internal consistency of the supplied Cargo metadata; it cannot prove the graph is complete or authentic, that every linked component was discovered, that discovered notice texts satisfy obligations, or that distribution is legally cleared.

On Omarchy ARM64 with Node `v26.12.1`, the missing-package and dangling-reference tests failed before their respective guards and all 12 notice-bundle tests passed afterward. The five Linux portable-packager tests also passed. A separate offline, locked, `aarch64-unknown-linux-gnu` Ratatui Cargo metadata graph was accepted: 69 resolved nodes and 69 indexed packages, with zero conventionally missing notice files reported by this tool. A prior local raylib metadata graph also indexed 50 of 50 resolved nodes. A separate older SDL3 metadata file was not qualified: its first-party path was outside this checkout and the existing containment guard rejected it. These counts are not a legal or system-library review. Metadata remains at `/tmp/pong-ratatui-notice-graph-20261113.json`; the previously generated local index remains at `/tmp/pong-ratatui-notice-index-graph-20261113.json`. No previous evidence was overwritten.
