# Notice bundle option validation

A Windows-filtered metadata scan was accidentally passed the string `'Windows'` as the third argument to `buildNoticeBundle`. JavaScript destructuring accepted the string and silently used the default `Linux` title, producing a misleading heading despite the correctly filtered graph. The affected excluded local artifacts and their hashes remain preserved, with corrections in the ggez and Nannou Windows pilot reports. A prior version of this report also listed bracket-lib; reinspection found that its retained bundle already had the correct Windows heading. The subsequently packaged raylib bundle used the explicit options object and has a Windows heading.

The builder now rejects a non-object options argument, null, arrays, unknown option keys and an explicitly undefined or unsupported platform. Omitting options still selects the historical Linux default; `{platform:'Windows'}` and other supported labels retain their established behavior. This guards the API shape, not the truth of the supplied platform or metadata graph, and does not constitute notice completeness or legal clearance.

On Windows Node 24.20.0, a new regression failed before the change and passed afterward. The notice and Linux portable test files produced 13 passes and six explicit platform skips (five Linux-only packaging cases and one POSIX symlink case). A real Windows-filtered offline locked raylib metadata graph still indexed 52 packages with zero missing-file flags and reproduced the Windows-labeled bundle SHA-256 `90daaeea9bdaaf4f7871aa2070a73aef513a38789f32f75541d624df67aaa0ef`; passing the former string argument now throws. Existing local bundles and packages were not rewritten. Linux-only packaging tests remain unverified on Windows.
