**Follow-up:** the [distribution trace](RATATUI-MUSL-DISTRIBUTION-TRACE.md) verified installed target inputs against official tarballs and identified the Rust source LLVM submodule. Source-to-object and complete notice review remain open.

2026-11-13, Omarchy ARM64. This investigates the [static musl experiment](RATATUI-MUSL-STATIC-OMARCHY.md), binary SHA-256 `e8fa5dea2c0a8724142dcb14ab639f67885507b10e5a59121234d7539bbdb1da`. It is evidence for further review, not policy clearance or a distribution approval. The linker-map rebuild matched that binary hash. Its map names 39 archives: 25 Cargo-target archives and 14 Rust-target-sysroot archives. These names are not necessarily every source component incorporated through LTO, generated code, native objects or compiler runtime.

## Cargo-built archives

All 25 Cargo archive names were mapped via their generated dependency files to exact versions in the locked musl-target metadata: 23 registry packages and two first-party packages. The [sanitized record](ratatui-musl-linked-cargo-audit-20261113.json) includes each archive, package/version, declared license expression and notice count. For all 23 registry packages the local `.crate` archive SHA-256 matched `experiments/ratatui/Cargo.lock`; all 1,199 regular members in those archives matched the corresponding cached source files after the build. The two local packages declare MIT. None of the 25 package expressions contains LGPL, MPL or GPLv3. This preserves alternatives as declared; it does not select a license or prove that all generated, native, inlined or compiler-supplied code is covered. The original record SHA-256 is `b440e1eb1b5c41b588cce852210671a4adad529b7e0af955cf6b91c3ba874953`, but its `link_map_sha256` field was wrong. The [corrected copy](ratatui-musl-linked-cargo-audit-20261113-corrected.json) changes only that field; its SHA-256 is `7727a1e9a81e5318a4bfe30a749783231d9349b586bf408206f9eafc78001e10`. The retained map and two independent records agree on `d26cedb28004ab7735a1ede1584de5fd3fab03037c91f66366fdbdd03f27b3cd`. The original record is preserved for history.

## Rust target runtime and compiler-builtins

The installed Rust target receipt identifies `rust-std 1.99.1 (58cf8f9c3 2026-10-13)` for `aarch64-unknown-linux-musl`. Its local channel manifest records the official target `.tar.xz` hash `2f3eb0d0610e2b7f6b2121d106e2490ac648decfa0c09b30873bdfc60de6c1ab`; this is a receipt/manifest value, not an independently retained copy of that distribution archive. The installed sysroot `libc.a` and `libunwind.a` hashes and link-map evidence are recorded in the [experiment](RATATUI-MUSL-STATIC-OMARCHY.md).

The Rust source revision reported by `rustc -Vv` is `58cf8f9c35b355199727627d07ae34a4e2846d67`. Its [standard-library lockfile](https://github.com/rust-lang/rust/blob/58cf8f9c35b355199727627d07ae34a4e2846d67/library/Cargo.lock) names candidate versions for six matching sysroot archive names. Their official registry archives matched the lockfile checksums and contain the declarations and notice-file hashes in [this sanitized candidate record](ratatui-musl-rust-sysroot-candidates-20261113.json), SHA-256 `e3763506368745156c90db3685b6d7cae93ef35f73702b74468883b47e68443a`. Three archives were fetched from the official crates registry; three were already cached. These candidate source records do **not** independently prove how the distributed rlibs were built.

At the same Rust revision, the source manifests for [std](https://github.com/rust-lang/rust/blob/58cf8f9c35b355199727627d07ae34a4e2846d67/library/std/Cargo.toml), [core](https://github.com/rust-lang/rust/blob/58cf8f9c35b355199727627d07ae34a4e2846d67/library/core/Cargo.toml), [alloc](https://github.com/rust-lang/rust/blob/58cf8f9c35b355199727627d07ae34a4e2846d67/library/alloc/Cargo.toml), [panic_unwind](https://github.com/rust-lang/rust/blob/58cf8f9c35b355199727627d07ae34a4e2846d67/library/panic_unwind/Cargo.toml) and [std_detect](https://github.com/rust-lang/rust/blob/58cf8f9c35b355199727627d07ae34a4e2846d67/library/std_detect/Cargo.toml) declare `MIT OR Apache-2.0`. The [compiler-builtins manifest](https://github.com/rust-lang/rust/blob/58cf8f9c35b355199727627d07ae34a4e2846d67/library/compiler-builtins/compiler-builtins/Cargo.toml) declares `MIT AND Apache-2.0 WITH LLVM-exception AND (MIT OR Apache-2.0)`. These are source-manifest declarations, not a completed object-by-object notice audit.

The revision's [ARM musl distribution Dockerfile](https://github.com/rust-lang/rust/blob/58cf8f9c35b355199727627d07ae34a4e2846d67/src/ci/docker/host-x86_64/dist-arm-linux-musl/Dockerfile) calls its [musl toolchain script](https://github.com/rust-lang/rust/blob/58cf8f9c35b355199727627d07ae34a4e2846d67/src/ci/docker/scripts/musl-toolchain.sh), which specifies musl 1.2.5 and patches; the [bootstrap source](https://github.com/rust-lang/rust/blob/58cf8f9c35b355199727627d07ae34a4e2846d67/src/bootstrap/src/core/build_steps/compile.rs) describes copying LLVM `libunwind.a` into the musl self-contained sysroot. This is evidence of the published source recipe, not a build attestation tying the installed archives byte-for-byte to that recipe. Exact musl source/patch provenance, the LLVM submodule revision and its license/notice correspondence to the installed `libunwind.a`, and other sysroot objects remain unresolved.

Several extracted `libunwind.a` objects and strings in `libc.a` record `GCC: (GNU) 9.4.0`. This records a compiler identity, not proof that GCC runtime code was linked or that a GPL license applies to those objects. The link map contains no named `libgcc` archive and the ELF has no dynamic section; it does contain `libcompiler_builtins`, `libc.a` and `libunwind.a`. The Rust compiler/linker and any compilers used to produce their target libraries are build tools; the exact static contents and notices of the shipped binary require separate verification.
