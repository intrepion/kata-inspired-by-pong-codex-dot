# Windows Fyrox MPL replacement feasibility

This bounded follow-up to the [Windows MPL tree audit](WINDOWS-MPL-TREE-AUDIT.md) inspected the locally cached Fyrox 1.0.1 manifests and sources. It did not modify the Fyrox experiment or any dependency. The owner's strict constraint remains a release blocker until target-specific dependencies and replacements are verified; source-tree or Cargo-graph presence alone is not proof of final linked code.

The current default Windows normal/build tree reaches MPL-2.0-declared Symphonia 0.5.5 through `fyrox -> fyrox-impl -> fyrox-sound -> symphonia`. The published `fyrox-impl@1.0.1` manifest has an unconditional `fyrox-sound` dependency. `fyrox-sound@1.0.1` unconditionally depends on Symphonia with `all-codecs`, and its public error and decoder code refer to Symphonia types. The existing Windows debug target contains Symphonia `.rlib` files, showing compilation in that target directory, but this does not prove which code survived final linking in a particular executable. The Pong adapter source did not contain `sound`, `audio` or `symphonia` text in this search; that does not establish that engine initialization or indirect dependencies avoid audio.

A separate minimal Windows MSVC fixture using `fyrox = { version = '=1.0.1', default-features = false }` failed `cargo check --offline` with unresolved `fyrox_impl`: the crate unconditionally re-exports that implementation when `dylib` is off. A second independent fixture with defaults off and the `fyrox-impl` feature explicitly enabled produced a normal/build dependency tree containing Symphonia through `fyrox-sound`. The second fixture's tree was generated offline with a new lock, not the Pong lock or a completed executable. Both fixture directories, logs, new lock and partial target are preserved in task workspace `fyrox-no-default-features-probe-20261113` and `fyrox-explicit-impl-probe-20261113`.

Thus disabling the top-level default feature is not a demonstrated usable no-Symphonia build. Potential next work is an upstream-supported no-audio engine configuration, or a carefully maintained engine/sound fork that removes or replaces the decoder while preserving required engine behavior. The latter is substantive: `fyrox-impl` references sound engine and scene types, and `fyrox-sound` exposes Symphonia errors and decoder interfaces. No such replacement has been implemented or validated, and no unsupported audio behavior should be silently stubbed.

The separate `option-ext@0.2.0` path through `directories@5.0.1 -> dirs-sys@0.4.1` has the same XDG-parser use pattern as the ggez-scoped 0.5.0 patch. A version-specific MIT/Apache dirs-sys patch is a candidate, but would not remove Symphonia and needs its own lock, Windows and Unix tests. No shared dependency patch was applied to Fyrox, and no MPL-free, clean-machine, legal or release claim is made.
