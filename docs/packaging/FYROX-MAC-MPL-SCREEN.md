On 2026-11-13, offline locked `cargo metadata --filter-platform aarch64-apple-darwin` for the Fyrox workspace at `e2b3cb455045a5c31b40539bf1b4980b91078cf3` yielded 401 packages. Git found no differences between those revisions in the Fyrox, core, scenario and benchmark crate paths or smoke scenario. This comparison does not establish all build inputs identical.

The target-filtered graph includes **15 packages declaring MPL-2.0**: `option-ext 0.2.0`, `symphonia 0.5.5`, and thirteen `symphonia-*` codec, format, bundle, core, metadata and utility packages at 0.5.5. No other license expression in this metadata text screen contained LGPL or GPL-3; all 401 had license expressions. These are declarations, and the graph includes build dependencies and can include code absent from the final binary.

Two normal-dependency paths from the actual locked graph are:

- `pong-fyrox → fyrox → fyrox-impl → fyrox-sound → symphonia`. `nm -m` of the tested executable showed numerous non-external text symbols with `symphonia_core`, codec, format and other Symphonia crate names, so Symphonia-named code is actually present in that executable. This is stronger than a metadata-only finding, although it does not prove every graph package's code is present.
- `pong-fyrox → fyrox → fyrox-impl → fyrox-ui → directories → dirs-sys → option-ext`. One `dirs_sys` symbol appeared; no `option_ext`-named symbol appeared in the filtered output. Inlining or stripped names can obscure code, so absence is not proof that option-ext is absent.

The exact cached manifests declare MPL-2.0 for Symphonia 0.5.5 and option-ext 0.2.0. The cached Fyrox 1.0.1 manifests show `fyrox-impl` depends non-optionally on both `fyrox-sound` and `fyrox-ui`; `fyrox-sound` depends non-optionally on Symphonia with `all-codecs`. Thus merely turning off optional codecs or changing the application’s sound usage is not shown to remove the MPL path. A different Fyrox configuration or maintained fork eliminating both paths would require implementation and fresh graph, binary, runtime and notice verification; none is claimed. The separately tested [Mac softbuffer](SOFTBUFFER-MAC-LICENSE-SCREEN.md) is a candidate implementation with no restricted declarations in its target metadata screen, but its system and complete license audit remains open. No release or deletion is authorized by this observation.

## Fyrox 1.0.1 feature-path follow-up

The cached published fyrox 1.0.1 manifest defaults to its fyrox-impl feature. Its wrapper source unconditionally re-exports fyrox_impl when dylib is off, so disabling defaults while leaving dylib off removes the dependency needed for the game API. The fyrox-impl 1.0.1 manifest exposes profiler and mesh-analysis features; sound and UI dependencies are non-optional, with no opt-out in the inspected manifests.

The cached crates' .cargo_vcs_info.json point to upstream revision f916d01304d945271b6d7d70569c1333f563a34f. At that exact revision, the [upstream fyrox-dylib manifest](https://github.com/FyroxEngine/Fyrox/blob/f916d01304d945271b6d7d70569c1333f563a34f/fyrox-dylib/Cargo.toml) depends non-optionally on fyrox-impl 1.0.1, and its [source](https://github.com/FyroxEngine/Fyrox/blob/f916d01304d945271b6d7d70569c1333f563a34f/fyrox-dylib/src/lib.rs) re-exports that implementation. The dynamic path retains the identified source dependencies and changes linkage. It was not built or inspected as a binary.

No feature configuration in the inspected 1.0.1 normal and dynamic wrappers eliminates both paths while retaining the same engine API. This source/manifest conclusion does not cover future versions or every possible source patch. No fork, deletion or release was made.
