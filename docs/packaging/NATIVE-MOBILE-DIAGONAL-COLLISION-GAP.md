# Native mobile diagonal paddle collision gap

2026-11-13, Omarchy ARM64. Source inspection found that the standalone [Kotlin game](../../experiments/native-kotlin/app/src/main/java/com/intrepion/pong/nativekotlin/Game.kt) and [Swift game](../../experiments/native-swift/Sources/PongCore/Game.swift) still decide a paddle hit using the ball's end-of-step Y position and the paddle's end-of-step position. They also put the ball at the paddle face after a hit without integrating the remaining step time. The shared Rust core evaluates contact at the face crossing and integrates the remainder. This is a source-derived mismatch and a concrete candidate gameplay defect, not a mobile-runtime reproduction.

For a stationary player paddle at Y=250, ball X=60, VX=-350, dt=0.033, the player face is X=52 and contact time is 8/350 seconds. With Y=180 and VY=600, crossing Y is approximately 193.714 (56.286 from paddle center, outside the 53-pixel contact threshold), but end Y is 199.8 (50.2 away): the native mobile source's endpoint test predicts a hit while the crossing-time test predicts a miss. With Y=215 and VY=-600, crossing Y is approximately 201.286 (48.714 away), while end Y is 195.2 (54.8 away): the endpoint test predicts a miss while the crossing-time test predicts a hit. Neither case crosses a wall. The Rust core's existing `paddle_collision_uses_height_at_face_crossing_on_both_sides` test passed here, and the original TypeScript crossing-height regression passed; a direct TypeScript run gave the corresponding miss/hit. The endpoint outcomes above are calculations from the Kotlin and Swift source, not execution of those languages.
