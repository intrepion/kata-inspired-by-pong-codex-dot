# Windows known-folder probe for the ggez profile check

A follow-up to the [ggez environment check](GGEZ-ISOLATED-HOME-WINDOWS.md) used `SHGetKnownFolderPath` with flags zero and the current process token to query local and roaming AppData. The committed `scripts/packaging/windows-known-folder-probe.rs` prints only HRESULTs and frees returned paths; it does not print profile paths. It was compiled with `rustc +stable-x86_64-pc-windows-msvc --edition 2021` using Rust 1.99.1. The tested probe source SHA-256 is `1a190e74010f025a83053dca76cfae74c6a163e3051ee1765d55382274561eef`, executable SHA-256 `5435416139a46bb6ee74cc6f5ffa1f5c6d1a10e8b2f5811dfa56d7a1e7595c95`.

With the normal host `USERPROFILE`, the native probe returned `0x00000000` for both folders. With `USERPROFILE` pointing to a newly created empty task-local directory, it returned `0x80070003` for local and `0x80070002` for roaming. With a separate task-local profile containing pre-created `AppData/Local` and `AppData/Roaming`, local still returned `0x80070003` while roaming returned `0x00000000`. The existing ggez release executable also exited 1 before telemetry under that structured-profile override, with the same filesystem error as before. No game rebuild or native input test was performed. The probe observes its own process and does not instrument the game; the exact failing call within ggez remains inferred from its dependency code and the matching results.

A PowerShell-hosted probe gave different results for the local folder under the same overrides, illustrating why process context matters. Known-folder queries created directories under the task-local profiles; all generated files, directories, probe source and binaries remain in `ggez-profile-api-windows-20261113`, with no cleanup. The results concern this host and artificial environment override, not a normal separate Windows account, clean-machine compatibility, accessibility or release qualification. No production fallback or Windows known-folder setting was changed.
