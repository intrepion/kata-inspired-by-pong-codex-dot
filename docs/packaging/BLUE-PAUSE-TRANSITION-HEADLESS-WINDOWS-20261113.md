# Blue Engine pause-transition trace: Windows headless fixture

An isolated worktree at checkpoint `46c6d6e9756a6956f4361dd1aacb0a3d05fe504d` added the [trace fixture patch](blue-transition-fixture-windows-20261113.patch) to adapter blob `e0ffafea38b919c37f7c08d7382c3f04ec57859c`. The fixture saves up to 16 consecutive headless texture buffers from callbacks after scripted tick 350 and logs the tick and game state observed at each callback before advancing the scenario. It does not change the game, renderer objects or scenario actions, but synchronous PNG writing changes callback timing. The fixture source Git blob is `17d489274a57d61658bb3ec086691fad7bd1d4fd`; its locked offline Windows MSVC release headless executable SHA-256 is `2aa6bfe609be84513177cee483a92f3fecb9dc7ba1fcca9371738ca822f96e64`.

In three runs, the first callback logged as Paused yielded a complete playing image with no pause text; the next logged Paused callback yielded the complete PAUSED and SPACE TO RESUME overlay. For the first run those were index 6/tick 363 and index 7/tick 375; the saved [first image](blue-transition-first-paused-windows-20261113.png) and [next image](blue-transition-next-frame-windows-20261113.png) have SHA-256 `28bec20494b7addb48ee00ccca888d008f53fb6028b68cef2ae89a163d88bb2d` and `283ffb35c2a773de1e377fc44d0e1dd94928318b5d34157ae450f8ab53b6134c`. In the other runs the corresponding logged ticks were 362/374. No partial pause overlay was observed in the inspected transition images. All three runs exited 0 with empty stderr and all 13 telemetry records matched `docs/evidence/rust-core-contact-timing-model-20261112.jsonl`.

In the cached Blue Engine 0.10.0 headless loop, `pre_render` occurs before changed-object updates and `renderer.render` occurs before the app callback; inspected `engine.rs` SHA-256 is `81bea14ef240fd4f4201f052659fa5eede0b1aa74aa8eba1a6c25034a3a1078e`. The images are app-owned headless buffers, and the logged state is callback state, not a synchronized presented-frame identifier. This observation is consistent with an update/render delay but does not establish its exact duration or a defect in native presentation. In particular, the windowed loop has a different callback/render order, so this does not reproduce or resolve the separate [Mac native transition concern](BLUE-TRANSITION-ORDER-MAC-20261113.md).
