# Piston, Fyrox and Miniquad focus-action audit — Omarchy, 2026-11-13

Piston and Fyrox paused on a reported focus loss but still accepted later queued keydowns. Both now track focus events and ignore live keydowns until a focus-gain event. Piston still processes releases to clear input; Fyrox clears held input on focus loss. Both preserve their previous startup assumption of focus until the first focus event. Their scripted/benchmark paths are unchanged.

A regression for queued resume and restart while unfocused failed before each fix and passed afterward, checking score preservation and subsequent focused resume. Full locked offline suites passed: Piston 14, Fyrox 8. Source Git blobs: Piston `c8ef43ccd9ab6ba62df3bc50db72fa71e2b432c0`; Fyrox `a686e308536bbe3e30d1c3a1193162f84fb8367d`. These are event-action boundary tests, not actual OS focus delivery, physical input, installed package or cross-platform qualification.

Miniquad's analogous keydown boundary also failed the regression, but no durable focus gate was published: the cached miniquad 0.4.11 macOS backend calls `window_minimized_event` on a window move as well as key-focus loss, and the move callback itself does not send the corresponding restored event. Treating every such callback as durable loss could leave controls disabled after moving a focused window. The existing Miniquad source (`77abb5d0d58a29be8003371853b86d204646d54c`) is unchanged. A reliable platform-specific focus signal or upstream correction and cross-platform runtime checks are needed before gating it safely. Existing data and artifacts remain intact.
