# ggez isolated-directory launch on Windows

On 2026-11-13 the extracted [Windows held-pause release pilot](GGEZ-HELD-WINDOWS-RELEASE-PILOT.md) executable, SHA-256 `3bf85d385fc754154480d9da73a8486ce8d9efc70e4b7fbd24e10609fcf1ce35`, was launched by absolute path in scripted mode from newly created empty working directories outside the package and repository. No binary was rebuilt. Host display, drivers, account, runtime libraries and unmodified environment variables remained available. These are not clean-machine or system-wide filesystem isolation tests.

With the normal host environment, the separate-working-directory control exited 0 with empty stderr, and all 13 telemetry records matched `../evidence/rust-core-contact-timing-model-20261112.jsonl` through finished tick 1440. Separate runs overriding only `HOME`, only `APPDATA` plus `LOCALAPPDATA`, or only `TEMP` plus `TMP` to new empty directories each also exited 0 with empty stderr and matched all 13 records. The exact stdout hash of the control is `8f792094be49929002f46fbbb163aa83e19147bbf02886ce1f1125fedeb9d3c6`.

A run overriding `USERPROFILE`, `HOME`, `APPDATA`, `LOCALAPPDATA`, `TEMP` and `TMP` together exited 1 before telemetry, with `FilesystemError("No valid home directory path could be retrieved.")`. A separate `USERPROFILE` plus `HOME` run and a `USERPROFILE`-only run each reproduced the same error; `HOME` alone did not. This is evidence for the specified environment overrides on this host, not proof of a failure under a normal Windows profile. The vendored ggez filesystem requires `directories::ProjectDirs::from`; the resolved Windows implementation obtains roaming and local AppData through `SHGetKnownFolderPath`. The specific failed Windows lookup and mechanism were not instrumented, so the cause remains open. Environment-only overrides are not a reliable substitute for a separate Windows account or known-folder redirection.

The three package payload hashes and manifest hash `83ae9fc678fe03af1caccc4f0ca798619f55ad4e0fbf5327d7a2d3d3ab522993` still matched afterward. The redirected profile, roaming, local and temp directories and each test working directory contained no regular files at the post-run inventory. This does not establish that APIs or drivers used those directories or that no files were written elsewhere. Logs and directories remain under task workspace `ggez-isolated-runtime-windows-20261113`; no cleanup was attempted. The package's 14 notice flags remain open. Scripted runs do not test physical input or accessibility; clean-machine behavior, complete notices, signing and distribution remain unqualified.
