# Ratatui musl runtime feasibility on Omarchy

**Historical:** Oliver subsequently approved the official target installation; the later [static musl experiment](RATATUI-MUSL-STATIC-OMARCHY.md) supersedes the toolchain blocker below.

2026-11-13, Omarchy ARM64. This is an investigation using existing local tools, not a new release, a completed musl build or legal clearance. No packages or toolchains were installed. The terminal implementation was chosen because it does not require a graphics or audio stack for its normal runtime; terminal emulator and OS behavior remain external.

The previously tested [Ratatui release binary](RATATUI-RELEASE-NOTICE-OMARCHY.md), SHA-256 `2e985f886e1480f7bf3bb3016ce10a1cf460ba30c1d36ea93db914d8d4684245`, is **not musl**: `readelf` reports interpreter `/lib/ld-linux-aarch64.so.1` and `DT_NEEDED` entries `libgcc_s.so.1`, `libm.so.6` and `libc.so.6`. On this host `ldd` resolves the latter two from glibc and the first from libgcc. Installed package metadata lists glibc as `GPL-2.0-or-later LGPL-2.1-or-later` and libgcc as `GPL-3.0-or-later WITH GCC-exception-3.1 GFDL-1.3-or-later`. These are aggregate package fields, not a component-level legal conclusion. `/usr/lib/libc.a` is owned by the host glibc package and is not a musl substitute. The [broader host inventory](OMARCHY-RUNTIME-LICENSE-INVENTORY.md) records its limitations.

The active stable Rust toolchain has `aarch64-unknown-linux-gnu` and `wasm32-unknown-unknown` targets installed, but not `aarch64-unknown-linux-musl`; no `musl-gcc`, `aarch64-linux-musl-gcc` or `zig` was found on PATH, and installed components do not include `rust-src`. A minimal `#![no_std]` probe using `rustc --target aarch64-unknown-linux-musl` failed with E0463, unable to find `core`. Thus even the target's core library is unavailable to this toolchain. This does not prove a musl route is impossible; it blocks building and checking one with the existing tools on this machine.

A locked offline Cargo metadata query filtered for `aarch64-unknown-linux-musl` succeeded without a compiler target installed. Its [sanitized resolved-package list](ratatui-musl-licenses-20261113.json) has 69 nodes; every node has a declared license expression, and none contains LGPL, MPL, GPL-3, GPLv3 or GPL-2.0-or-later. The list SHA-256 is `b7883c4c65aa915394ea18063abf1a8c6a5e235ea111e97418f5c7fc0d9716ff`. This metadata includes build/optional nodes and is not evidence of actual linked components or the license of a future musl runtime, linker, compiler-builtins or all source/notice files. Alternatives were not selected. The query used the current Ratatui manifest and lockfile; no musl executable or runtime-linkage result was produced.

The probe source, stderr, raw metadata and sanitized list remain at `/home/intrepion/Documents/Codex/2026-11-12/task/pong-musl-feasibility-20261113`. The next qualified step requires an authorized source of the ARM64 musl Rust target and suitable linker/runtime, followed by a fresh locked build, actual ELF/interpreter and static-linkage inspection, target-specific notices and runtime tests. Under the current existing-tools-only constraint, those steps remain blocked; no package was published and no implementation or user data was removed.
