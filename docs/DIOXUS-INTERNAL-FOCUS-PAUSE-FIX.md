# Dioxus internal-focus pause fix

On Omarchy ARM64, a fresh locked offline Dioxus web debug build from `fa6606fc3b999d1a39a7941774b7aeb1bd6c95bd` reproduced the issue in Chrome served from localhost: after Start and focusing the court, the first Pause / Resume click left the game playing; a second click paused it. The before WASM SHA-256 was `9c266542830813223a1aea276cdaa40228025a058bd83f10cf8dd77f1b52f0eb`.

Dioxus focus-event data lacks a related target on desktop, so this uses its document API to check focus after the browser finishes the focus transition. The shared policy ignores focus moving within the game and pauses/clears input when focus leaves it. If the check fails, it conservatively pauses. This deferred check has a scheduling boundary and is not a proof of all platform focus behavior.

A rebuilt localhost Chrome debug web build, WASM SHA-256 `ae634357786b4711dfd350106e9d7d5b2df0b6356b6d84f816c4e4060fb15e65`, was checked with supported browser actions: after focusing the court, one Pause click displayed Paused, the next resumed, and clicking outside the game paused it. These are bounded automated browser interactions, not physical input or multi-window focus qualification. Both browser tabs and localhost servers were closed after testing.

The locked offline desktop check and debug build also passed using the existing local libxdo dependency; desktop executable SHA-256 `78305bc2ff32bfa7d23cc10499cc76b4c5a5e46921495fb76831530b0816e365`. Its separate scripted run exited 0, matched all 13 Rust model records, and produced six SVG scene sources; those are app-owned source exports, not screenshots or native interaction. All 13 shared-controller tests passed. No desktop input, physical input, other browser/OS, package, focus-loss timing or release qualification is claimed.
